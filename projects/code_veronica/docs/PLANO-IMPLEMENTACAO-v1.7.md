## Prepass reuse for repeated draws (P6 follow-up, branch melhorias-v1.7)
Why: in gunfire rooms (0x0204/0x0205) a frame is 13-16k tiny draws that collapse into ~200-400 runs of 35-60 draws with identical (pso, textures, target, vertex format); the CPU render thread spends ~6 ms in the prepass and ~8 ms recording. The prepass resolved every draw's texture views from scratch (79k texture units bound per frame for only ~230 texture-set changes). v1.6.1 already reused the pipeline lookup between identical draws (prep_reuse_on, `previous_draw`, live verification); this extends the same idea to the rest.

What is reused (all inside ONE prepass_range call, from the draw just prepared to the next one; nothing is carried across calls or frames):
- Texture step (new function prepass_tex_units, same code as before, moved out of the loop): when the next draw has byte-identical texture units (all 8: offset, raw offset, size, format, remap, address, pitch, mips, cube, set), the same program snapshot (fp_addr, fp_snap, fp_bytes; a snapshot offset is deduplicated by content when recorded, so equal offset = equal bytes), and the same target offset, the resolved views (SrvReq x8), the sampled-target indices (tex_rt), the feedback-risk flag and the texture-gamma words are copied. The gamma word is written into THIS draw's own b1 slot (cb_slot differs per draw), so it is replayed, not shared. srv_commit still runs and still folds identical windows.
- Pipeline lookup: the v1.6.1 reuse (needs 60 FPS pose mode, as before) no longer compares the program bytes when both draws point at the same snapshot offset (same pointer = same bytes); the live checks of fp_prepared_ready are unchanged.
- Not a reuse but the same hot path: getenv("TEX_DUMP") ran once per bound texture and getenv("FP_CONSTBUF") twice per pipeline lookup; both are now read once.

Invalidation (when a draw does NOT reuse and runs the original path): the first draw of a call; after a clear/copy/non-VP record; any change in the key above; a previous draw that could not get a texture slot (budget/slots exhausted); texture replacement or dump packs on (their loading state changes between draws); a reduced-viewport capture present (the code samples guest memory); a snapshot-less program (its used-unit mask comes from guest memory); any texture debug env (TEX_BUDGET, RTT_VIEWRT, EMPTYTEX, SCREEN_AS_TEX, TEX_DUMP, TEX_BINDDBG, RT_NOGAMMA); outside native 60 FPS pose mode unless CV_PREP_REUSE=1 (same gate as v1.6.1, so the 30 FPS comparison package is untouched). Texture CONTENT: inside one call the texture-slot cache answers "already bound this frame" for any slot it handed out, so the bytes are not re-checked there either; a changed guest texture is picked up by the first draw that binds it (a miss), exactly as before. Render-target textures: the sampled-target index depends on the render-target table, which only changes between prepass calls, never inside one.

Switches: CV_PREP_REUSE2=0 turns the new reuse off (default on); CV_PREP_REUSE=0 turns off everything (v1.6.1 and this). Dev only (absent from distribution builds): CV_PREP_VERIFY=1 recomputes every reuse hit the normal way and compares (views, target indices, feedback flag, gamma words; for the pipeline: pointer and cache index); a difference logs [PREP-REUSE-MISMATCH] draw=.. step=tex|pso, the fresh value is used, and it is counted. CV_DRAW_SPIKE reports per spike frame: `prepass steps (ms, est...)` = head/vtex/tex/srv/pso/other (TSC share of the measured prepass time) and `prepass reuse: hits= misses= mismatches=` (with the tex and pso split).

Record phase (analysed, nothing added): the draw loop already skips SetPipelineState, viewport/scissor, the texture descriptor table and both constant-buffer views when equal to the previous draw's (last_pso, last_vp, bound_srv, bound_cb0/cb2). What remains per draw is the per-draw root constant (vertex offset), DrawInstanced and the per-draw target lookups; none can be skipped without changing what is submitted. A cache for off_rt_find_sz per draw was rejected because the render-target table changes inside the record loop.

A/B test with capturar-shaders-live.cmd: run once with `set "CV_PREP_REUSE2=0"` (uncomment that line) and once with the default, in the same scene (same room, same weapon, same burst). ### Prepass reuse: gate fix after the first in-game capture
The first capture showed `hits=0 misses=0`: the reuse never ran. Two causes. (1) The v1.6.1 pipeline reuse required `s_pose_on`, which is set only by legacy pose interpolation (CV_RENDER_INTERPOLATION=1 plus CV_FPS_TEST_60=1); smooth animation + frame generation (`legacy_pose_interpolation=off`) never sets it, so the pipeline reuse was off for this configuration even though `prep_reuse_on()` itself was on (CV_FPS_TEST_60=1). (2) The texture-step reuse was disabled whenever texture replacement was on, and the PT-BR translation pack (CV_PTBR_TEXTURE_DIR) keeps it on permanently. It now stays on: per hit, every unit that consulted the replacement lookup asks again and any difference in the answer (async load finished) is a miss; dump-on is checked per draw. A reduced-viewport capture no longer disables it globally, only draws whose units match a captured size. The spike report line now ends with `gate(calls): open=.. off[CV_PREP_REUSE2=0]=.. off[debug env]=.. off[prep_reuse_on false]=.. off[CV30 package]=..`.


## Draw-run merging (record phase, branch melhorias-v1.7)
Why: after the prepass reuse the biggest CPU cost in automatic-weapon fire (rooms 0x0204/0x0205: 13-16k draws, 8-11 ms of the frame in the record loop) is one DrawInstanced plus one root constant per draw, for ~16k tiny draws (mean ~19 vertices) that form only ~300-400 runs of consecutive draws with identical state (the `B=A+vtx+vcb_same` run line of the spike report: mean run 33-50 draws).

What a draw is (analysis of the record loop): every VP draw is a non-indexed DrawInstanced(count, 1, first, 0) over vp_vb slots of 256 bytes (the record stage expands indexed draws, strips, fans and quads into plain triangle/line LISTS, so a record's topology is only TRIANGLES or LINES). Per-draw state: pipeline (fp snapshot + vertex program + blend/cull/mask/depth key), viewport/scissor (guest rect), the t0-t7 descriptor window and the vertex-texture window, root CBV b0 (vertex constants, slot `vcb_slot`, shared by consecutive draws when no constant changed) and root CBV b1 (fp constants + texture words + alpha test, slot `cb_slot` = the record index, so a DIFFERENT address per draw even when the contents are identical), the vertex-offset root constant (index 5; with RSX_GPU_VFETCH the shader reads record `first + SV_VertexID`), the colour/depth targets. The loop already skips SetPipelineState/viewport/SRV table/CBV when equal to the previous draw's.

Rule: draw b joins the run whose last draw is a (one decision per run, submission order, nothing reordered) only if ALL of these hold (function `dm_pair`):
- both are plain VP draws (no clear, copy, legacy record);
- identical pipeline inputs: topology, vs_idx, fp_addr, fp_snap (non-zero: the same frozen program bytes, so the same inline constants), fp_bytes, fp_exp32, cull, cmask, blend, blend_key, dtest, dfunc, alpha_ctl, textured, tex_slot;
- identical 8 texture units (off, raw, w, h, fmt, ctrl1, addr, pitch, mips, cube, set), identical sampled-target indices, identical SRV window index, identical vertex-texture set (mask, window, hashes, shapes);
- the same vertex-constant slot (b0 address);
- b1 byte-identical: everything vp_record_cb writes there is a function of the record fields compared above plus the texture-gamma words the prepass adds, which the prepass now stores exactly per draw (DmInfo) and which must match; the lighter-probe target (a live flag is written into b1) is never merged;
- identical render targets (rt_off, MRT offsets, size, format, zeta, pitch) and viewport rect; no feedback hazard (the prepass flagged neither draw, no unit samples the bound target);
- a LIST topology and a whole number of primitives in a (3 vertices for triangles, 2 for lines; otherwise b would start out of phase), non-zero counts;
- contiguous vertices: b.vb_byte_offset == a.vb_byte_offset + a.vertex_count * 256 (the merged call passes the first draw's offset with the summed count; the vertex shader fetches record first+SV_VertexID, i.e. exactly the records the single draws read);
- the summed count stays <= 0x40000 vertices (cap);
- b is inside the prepared range and before the command-list split point and any depth-conversion/FSR boundary; the shadow/depth-of-field/letterbox filters would not drop b; the pipeline the prepass prepared for b is the same pipeline object as a's.
Without RSX_GPU_VFETCH the input assembler reads consecutive vertices from the same start, which is equivalent unless the vertex program uses SV_VertexID itself (a program with no vertex attributes): such programs are never merged. The merge is off for the whole frame while any per-draw capture/probe is active (rsxcap steps, pipeline-statistics queries, frame-detail, cutscene diag, DRAWARGS, VP_SUBMIT, RT_REBIND, RT_CLEARDBG, VP_TESTTRI, FP_ZERO_K). The existing shadow batcher (CV_SHADOW_BATCH, which already merges its generator draws) runs first and is left as it was.

Switches: CV_DRAW_MERGE=0 turns it off (default on; also in distribution builds: windows_entry.cpp clears only developer variables and this one is not in its list). Dev only (absent from distribution builds): CV_DRAW_MERGE_VERIFY=1 re-checks every merged run pair by pair with separate field-by-field code (`dm_verify_pair`); a failure logs `[DRAW-MERGE-VIOLATION] draw=N (run started at S, K draws) field=NAME` and that run is issued draw by draw. ## Run-level prepass and record (branch melhorias-v1.7, after draw-run merging)
Why: after the per-draw reuse the prepass still walked every draw (~6.4 ms in a ~13.9k-draw burst frame: head 0.5, vtex 0.6, tex 1.9, srv 0.7, pso 2.3) and the record loop still compared every draw with its successor to decide merging (~6.2 ms). The ~360 groups of identical consecutive draws are decided ONCE, in the prepass, and the record walks groups.

Prepass (prepass_range): a draw joins the group of the previous draw when `dm_pair_x(prev, d, run_v, derived=0)` says DM_OK, i.e. the dm_pair rules on the record fields only (pipeline inputs, 8 texture units, vcb slot, targets/viewport, vertex-texture mask, list topology with whole primitives in the previous draw, contiguous vertices, vertex total <= 0x40000, no lighter probe, no SV_VertexID program) and `lead_last + 1 == d` (the previous draw is in the group). Such a draw is *covered*: no head probes, vtex, texture views, srv_commit or pipeline lookup. It copies from the leader: `s_srv_win`, `s_prepared_fp` (pipeline index/key), `s_dm_info` (feedback flag + gamma words), `tex_rt[8]`, and writes the leader's gamma words into ITS OWN b1 cell (`cb_slot` differs per draw), so a covered draw that the record does not merge is drawn exactly like a normally prepared one. The leader keeps `s_run_last[lead]` (last member) and `s_run_verts[lead]` (vertex total).
A draw becomes a candidate leader only if: no vertex textures (`vtex_mask == 0`, not covered at all: "prepare normally when in doubt"), no feedback risk, a texture result that is memoisable (`tm.valid`: no texture slot shortage, not a reduced-viewport capture hit, program frozen in the arena), a frozen snapshot and a valid prepared pipeline. The group breaks (the next draw prepares normally and becomes a new leader candidate) on: a clear/copy/non-VP/legacy record, any dm_pair state/vcb/rt/vtex/topology/contiguity/phase/cap difference, the start of a prepass_range call (parts of a split frame are separate calls; nothing is carried across calls or frames). Groups only form when `gate == 0` (same gate as the texture/pipeline reuse: CV_PREP_REUSE2 not 0, no texture debug env, native 60 FPS or pose, no explicit CV30 package), `CV_DRAW_MERGE` is on, texture dump is off, and the frame has no per-draw capture/probe (rsxcap steps, pipeline-statistics queries, frame-detail, cutscene diag, DRAWARGS, VP_SUBMIT, RT_REBIND, RT_CLEARDBG, VP_TESTTRI, FP_ZERO_K, RSXCAP_STEP_*, DEPTH_CLEAR_ON_SWITCH). Texture-replacement staleness (the PT-BR pack) is not re-asked per covered draw: the answers only change in texrep_frame (before the prepass) or when the user toggles the pack; the leader's own lookup is fresh.

Record (draw loop, inside the existing merge block): for a leader with `s_run_last[d] > d` and no per-draw filter on (shadow-map neutralising, depth-of-field off, no-letterbox: with any of them the old pair-by-pair scan runs), the loop checks only what the prepass cannot know: `fp_prepared_ready(d)` equals the leader's `dpso` (live pipeline, not pending), the group's textures do not include the bound colour target, then clamps the group end by `pp_done`, the command-list split (`split_n`), the FSR depth point and every depth-conversion point, and issues ONE DrawInstanced with the stored vertex total (recomputed by summing only when the group was clamped). The same viewport/scissor/SRV/CBV/pipeline commands as the first draw are emitted (they were already deduplicated per draw), then the loop jumps `d` past the group. A draw that is not a leader (for example the rest of a clamped group) takes the old per-draw scan, so every case that is not decided in the prepass behaves as before. The shadow batcher still runs first and is untouched; clears, copies, legacy records and barriers are never in a group.

Switches: `CV_DRAW_RUNS=0` turns the whole thing off (prepass per draw + the draw-run merging exactly as before; default on; also in distribution builds: windows_entry.cpp clears only developer variables and CV_DRAW_RUNS is not in its list, same as CV_DRAW_MERGE). `CV_DRAW_MERGE=0` and `CV_PREP_REUSE2=0` still switch everything related off (no groups form). Dev only: `CV_DRAW_RUNS_VERIFY=1` makes every covered draw run the complete old prepass (fresh texture resolution, srv_commit, vp_get_fp_pso) and compare with what the cover copied (SRV window, sampled-target indices, feedback flag, gamma mask/values, its b1 cells, pipeline index/key/pointer); any difference logs `[DRAW-RUNS-MISMATCH] draw=N run=R field=NAME`, the fresh value is used, the group closes there and `mismatches` counts it. It also turns on the record-side `dm_verify_pair` check of every group (logs `[DRAW-MERGE-VIOLATION]`; the group is then issued draw by draw). Slow by design.
Spike report (CV_DRAW_SPIKE) new lines: `pso sub-steps (ms, est.)` = key+snapshot / reuse-match+ready / full lookup (vp_get_fp_pso) / bookkeeping, `prepass steps ... cover=`, `runs: groups= led= covered_draws= prepass_ms_saved_est= | broke[...] | no-leader: ...` and `runs(actual): enabled= verify= mismatches= | this frame: prepass_covered= record_groups= record_draws_in_groups=`. The existing `ms:`, `prepass steps`, `prepass reuse:`, `merge:` and `merge(actual` lines are unchanged.

A/B test (capturar-shaders-live.cmd): same room, same weapon, same burst (rooms 0x0204/0x0205). Run once normally and once with `set "CV_DRAW_RUNS=0"` (uncomment); compare `ms: total/prepass/record` and the `runs:` lines in build-release\bin\draw-spike-log.txt. Correctness: capturar-shaders-verificar.cmd (sets CV_DRAW_RUNS_VERIFY=1 with the other verifications); send every `[DRAW-RUNS-MISMATCH]`, `[DRAW-MERGE-VIOLATION]` and `[PREP-REUSE-MISMATCH]` line (expected: none) plus the `runs:` and `runs(actual` lines; the image must be identical.
Expected gain (not measured): prepass 6.4 -> about 1.5-2.5 ms (a cover costs one dm_pair_x call, ~ a memcmp of the 8 texture units and ~40 compares, plus copying ~100 bytes; the ~360 leaders still cost their full path), record 6.2 -> about 2.5-3.5 ms (per group: the leader's retarget/pipeline/viewport work and one draw; the pair-by-pair scan is gone). Uncertainty: if `no-leader` or `broke[...]` counters are large (vtex, feedback, no-pipeline-or-memo, state) the real group count is lower than the 360 of the earlier analysis. The `pso sub-steps` line says where the 2.3 ms of the pso step goes; nothing in it was optimised (a covered draw skips it entirely).
